设计探讨轮里我用 AskUserQuestion 抛结构化选项，用户先回「你还没问我是
什么想法呢」，再回「等我说完」——他要先完整陈述自己的想法，然后我才
回应/给选项。2026-08-23 的「大题转换模式」讨论即此模式：我先摊现状+
弱点清单，用户逐条表态（有的解释设计意图、有的拍板「这个好加」、有的
确认是问题），我按表态直接实现或留方案待议。另外用户会突然下节奏口令
（「稍等，你先拉取」= 立即停下手头编码先同步 git）。

设计类交付的对应形态（同日易混词设计任务确认）：用户明说「你设计完成
后，给我一个文档，我审核一下」——先出审核文档，末尾列编号的待拍板
决策点，等他逐条过完再动代码；实施中途来了设计请求也要先暂停实施、
出设计稿（word-timing 实施即为易混词设计审核暂停）。

**Why:** 用户对产品有完整的个人构想（如 steps 题四选项是「心算不能算，
只能验证」的有意设计），过早给选项框会打断他表达；节奏口令通常是并行
会话/合并时机有了新情况。

**How to apply:** 讨论轮输出「准确的现状地图+弱点+我的推荐」后**停住等
用户说**，不用选择题工具催；用户逐条表态后按表态执行（授权的直接做，
确认是问题的给方案待确认）；收到「稍等/先拉取」类口令立即暂停实施、
先做同步动作。报 bug 的形态（2026-08-27 两例）：用户常**只贴 DOM 快照 +「修复一下这个bug」不描述症状**——从 DOM 结构、部署目录未压缩 i18n、
minified bundle 上下文反推症状（如剩余数与学伴画像矛盾、计时器恒三十
几分），别反问「什么症状」空转。参见 [[feedback-delegate-decisions]]、
[[wengu-steps-design-intent]]。
