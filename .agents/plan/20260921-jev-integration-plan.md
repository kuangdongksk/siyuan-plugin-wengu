## 〇、先说人话：Jev 是什么、凭什么适合这个插件

咱们插件现在用的 AI（转换出题、学伴台词）是「作文型」的：喂一大段材料，它回
一大段文字，代码还得自己解析、还得防它格式跑偏。

Jev 是另一种：**只做判断题的模型**。给它材料 + 一组问题，它只回结构化答案——

- **是/否**（noul）：`{答案: 是, 概率: 0.93}` ——概率就是它觉得「是」的把握；
- **单选**（choice）：从你给的选项里挑一个，附每个选项的概率和总体置信度；
- **打分**（score）：按你定义的 1~5 档打分，每档有具体情形描述。

它不写文章、不解释、不跑题。好处三个：**快、便宜、格式永远不坏**。而且置信度
是显式的——把握不足时代码能选择「不当家，交给人」。

一个具体例子：转换出的题目「下列哪项是等差数列…」+ 原文段落，问 Jev
「这道题的答案能否从材料唯一推出？」它回 `{是, 0.91}`——烂题在落库前就被点名，
而不是等用户刷到再骂街。

## 二、插件内怎么加（三个板块）

### A. AI 转换质检（convert 域）

**现状**：转换弹窗把文档切片 → AI 出题 → 解析（BankParse）→ 落题库。
烂题（答案不唯一、题干推不出、和材料无关、题型转错）会直接进库，刷到才知道。

**加法**：每片题目解析成功后、落库前，把「片内全部题目 + 材料原文」打包发给
Jev **一次请求**批量问（独立问题并行是它的原生能力）：

| 问题     | 类型  | 判什么                                              |
| -------- | ----- | --------------------------------------------------- |
| 答案唯一 | noul  | 答案是否唯一成立，没有「也对」的干扰项              |
| 可推出   | noul  | 题干答案能否从材料推出（不靠外部知识）              |
| 材料相关 | noul  | 题目和这段材料是否匹配（防 AI 凭空编题）            |
| 题型正确 | noul  | 单选/多选/填空有没有转错形                          |
| 质量分   | score | 1~5，档位写死具体情形（如 1=答案错误 5=可直接入库） |

**置信度政策（写死在代码里）**：任一 noul 概率落在 0.2~0.8 之间、或 choice/score
置信 <0.7 → **不拦截、不删题**，只在转换报告里给这题标「Jev 存疑」加一句原因；
概率明确踩雷（如可推出 <0.2）同样只标不删——**静默丢数据违反数据演进守则**，
删不删永远是人点。

**落点**：新逻辑放新文件（`src/ai/jev/` 客户端 + `src/ai/jev/convertChecks.ts`），
`src/convert/service/run/ConvertBatch.ts`（已 492 行，接近 500 红线）只加一行
调用。转换报告的标注展示走现有报告组件加一列。

**没 key / 调用失败**：整段质检静默跳过，行为与现状逐字节一致。

**成本量级**：一片一次请求（一片通常 3~10 题），千字文档多两三次判定调用，
秒级返回——Jev 是判定模型，不是长文本生成，延迟远低于出题那次 AI 调用。

### B. 复习天数（word 域背单词的 AI 复盘）

**现状**：复习天数由 `src/word/core/WordFsrs.ts` 的 FSRS 步进算（d/s/due =
难度/稳定度/到期），**公式是确定性的，不由 AI 定天数**。已经有一个「AI 复盘」
入口（生成侧 `src/word/service/WordAi.ts` + prompt 在 `src/ai/prompts/misc.ts`，
落盘侧 `src/word/core/WordStore.ts` 的「AI 复盘结果落盘」）：AI 只给 up/keep/down
三档动作，代码按比例挪稳定度——注释里写明「不凭空给天数」。

**加法**：把 AI 复盘的生成侧从「作文型 AI 回文字 → 代码解析」换成 Jev 判定：
给词 + 复习记录（对错流水、间隔），问一个 choice——
「这个单词下次复习该 up（拉长间隔）/ keep（维持）/ down（缩短）？」
外加一个 noul——「上次答错是不是手滑而非没记住？」。

**好处**：格式永不错（不再需要解析自由文本）；每档带概率，低置信的词**维持
原稳定度不动**（比现在「解析失败就整批放弃」更细腻）。

**边界（重要）**：间隔公式本身一行不动；Jev 只影响「选哪一档」这一个口。
确定性优先、可复算、可回滚。

**quiz 错题复习明确不加**：错题本复习按轮次走、没有「天数」概念，没东西可调。
写在这里防止过度设计。

### C. jevkey 设置

- `src/ui/SettingsDialog.ts` 的 `WenguSettingsShape` 加 `jevKey?: string`——
  optional 字段只加不改名，符合数据演进守则，存量 settings.json 零迁移。
- `src/index.ts` 的 `WenguSettings` 镜像同步（装载 backfill 同款）。
- 设置页「AI 转换」分组加一行**密码框**（FormHtml 行样式，遮显切换）。
- 安全口径：key 只存 settings 存储（思源 saveData），不进日志、不进题库/词书
  数据；审查 PR 时 diff 里出现 key 直接打回。
- **没填 key = 所有 Jev 功能静默关闭**，各环节走各自的降级路径（A 跳过质检、
  B 走现有 AI 复盘或跳过、预检脚本在 CI 自动跳过）。

### D. 明确暂不做（防过度设计）

- **做题实时判分**：判分已有确定性规则，且作答延迟敏感，不塞网络调用。
- **Jev 判定结果落盘/缓存**：第一版一律现算不存。按数据演进守则，任何新落盘
  都要配版本闩和 backfill——在「标注一下」这种价值量级上不值，等真有「离线
  看历史判定」的需求再说。
- **移动端专属差异**：jevKey 是全局设置，移动端天然同享，无特殊分支。

**每单验收标准（写进 Issue）**：

1. 无 key 时行为与现状一致——现有全部测试不改一行仍绿（这是硬验收）；
2. 有 key 的判定路径带单测：mock `fetch` 覆盖 正常/401/429→降级/网络失败 四路；
3. 置信度政策有单测钉死（低置信必须走降级分支）；
4. CI 五件套全绿；动到入口/依赖才需补 `pnpm build`（单 1 不动依赖，不需）。

## 四、风险与对策

| 风险            | 对策                                                                           |
| --------------- | ------------------------------------------------------------------------------ |
| Jev 判定不准    | 所有环节低置信/踩雷都只「标注或维持现状」，删除/改天数永远在人或确定性代码手里 |
| key 泄露        | 只存 settings；不落日志；CI 注入走私有仓库 imports 不进本仓库                  |
| 服务不可用/限流 | 429/529 退避重试一次，再败走降级，不弹窗轰炸                                   |
| 成本失控        | 批量问（一片/一批评一次）；判定模型按输入计费，量级远低于出题                  |
